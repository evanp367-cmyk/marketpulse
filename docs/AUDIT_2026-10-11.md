# MarketPulse: аудит и восстановление локальной среды

Дата: 11 октября 2026. Исходный коммит: `e558073` (MarketPulse 0.4.9).
Проверка выполнена в облачной среде Codex, без подключения к VPS, рабочей базе,
реальному боту и платёжной системе. Это результат первого этапа, не заключение
о готовности всего продукта к публичному запуску.

## Фактическая карта проекта

| Область | Файлы и назначение |
|---|---|
| API | `backend/app/main.py`: FastAPI, HTTP-маршруты, тарифные ограничения, создание схемы при старте |
| Авторизация | `backend/app/core/auth.py`: серверная HMAC-проверка Telegram initData и отдельный режим разработки |
| Настройки | `backend/app/core/config.py`, `.env.example`, `.env.vps.example` |
| База | SQLAlchemy asyncio; SQLite для разработки, asyncpg/PostgreSQL для VPS |
| Таблицы | User, WatchlistItem, PortfolioPosition, AlertRule, Subscription, Payment |
| Источники | `providers/`: Binance Spot, ЦБ РФ, Frankfurter, RSS CoinDesk/Cointelegraph |
| Расчёты | `indicators/calculations.py`, `portfolio/valuation.py` |
| Telegram | `telegram/bot.py`: polling aiogram 3, `/start`, `/terms`, `/paysupport`, обработка оплаты |
| Интерфейс | React 18, TypeScript, Vite 6, Lightweight Charts 5; большая часть интерфейса в `App.tsx` |
| Развёртывание | Dockerfile, Compose: db/api/bot/caddy; статический frontend через GitHub Pages |
| Миграции | Alembic установлен как зависимость, но конфигурации и миграций нет; используется `create_all` |
| CI | Публикация frontend; backend-тесты в workflow не запускаются |

Репозиторий был чистым. Зависимости Python заданы диапазонами без lock-файла;
frontend имеет `package-lock.json`, установка выполнена через `npm ci`.
Проверено на Python 3.12.14, Node 24.19.0, npm 11.9.0; CI использует Node 22.
`FEATURE_STATUS.md` и часть roadmap описывают 0.3.0, поэтому не являются
актуальным подтверждением возможностей 0.4.9.

## Подтверждённые ошибки и выполненные исправления

1. **HTTP 500 при параллельном первом входе.** Несколько запросов одновременно
   вставляли одного Telegram-пользователя, нарушая уникальность `telegram_id`.
   После конфликта транзакция откатывается и читается уже созданная запись.
   Аналогично защищено создание первой подписки. Проверены 20 параллельных
   запросов для каждого сценария на SQLite и PostgreSQL.
2. **Несогласованное автопродление Stars.** Удалён `subscription_period` из новых
   счетов; условия бота теперь описывают разовую оплату 30 дней. Регрессионный
   тест проверяет фактическое тело HTTP-запроса через `MockTransport`.
   Существующие подписки в Telegram не изменялись.
3. **Нулевая стоимость портфеля без цен.** Ранее сумма отсутствующих котировок
   возвращалась как `0`. Теперь возвращается `null`, интерфейс показывает `—`
   и объяснение. При частичных ценах отображается предупреждение о неполной оценке.
4. **Скрытый отказ новостей.** RSS API возвращал `warnings`, но UI их игнорировал.
   Теперь видны предупреждение и пустое состояние. Проверено отдельной браузерной
   подстановкой ответа об отказе; рабочее приложение не использует фиктивные новости.

Исходные файлы, изменённые на этом этапе: `core/auth.py`, `main.py`,
`portfolio/valuation.py`, `telegram/bot.py`, `frontend/src/App.tsx`,
`frontend/src/api.ts`. Добавлен `backend/tests/test_api_workflow.py`, расширен
`backend/tests/test_portfolio_valuation.py`. Зависимости, lock-файл, Dockerfile,
Compose и схема БД не изменены. Изменения локальные, без commit/push/deploy.

## Разбор известной проблемы VPS

Compose требует `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `API_DOMAIN`
до запуска сервисов. `.env.example` — локальная SQLite-конфигурация и не содержит
этих production-полей. Для VPS предназначен `.env.vps.example`, где значения
токена, пароля и публичных адресов необходимо заменить настоящими.

Наличие `/opt/marketpulse/.env` на VPS в этом сеансе не проверялось: разрешения
на серверные действия нет. Локальный `.env` создан только из development-примера,
игнорируется Git и не предназначен для VPS. Секреты не выводились и не создавались.
Тестовый PostgreSQL использовал отдельную локальную БД и loopback-порт, без
производственных данных. Не переносить его тестовую trust-авторизацию на VPS.

После отдельного разрешения: сохранить существующий `.env` и данные, заполнить
отсутствующие production-поля через защищённый редактор, проверить
`docker compose config --quiet`, затем запускать согласованные сервисы и проверять
логи, DNS, HTTPS и Mini App. Пароль можно сгенерировать на сервере командой
`openssl rand -hex 32`, сохранив результат только в защищённой конфигурации.
Базу и volumes не сбрасывать; `docker compose down -v` не использовать.

## Следующие этапы

1. **P0: база и эксплуатация.** Добавить Alembic и безопасный переход существующей
   БД на версионированную схему; проверить backup/restore на отдельной копии.
   `/health` сейчас не проверяет БД. Добавить отдельную readiness-проверку,
   защиту публичных API от чрезмерной нагрузки и backend-тесты в CI.
2. **P1: портфель.** Спроектировать журнал операций с Decimal, датами, редактированием,
   пересчётом средней цены и изоляцией пользователей; миграции предшествуют UI.
3. **P1: рынок и сигналы.** Общий кэш/поток Binance с ограничением частоты,
   актуальность данных, таймфреймы графика и корректные валюты пары;
   затем worker условий, история и дедупликация сигналов.
4. **P1: новости и уведомления.** Кэш, категории/поиск/активы, честные статусы источников;
   затем лёгкий и проверяемый анализ тональности. Доставка Telegram с повторами
   и cooldown, управление правилами и история. Не добавлять платные сервисы.
5. **P0 перед монетизацией:** проверить конкурентную обработку платежей, возвраты,
   срок доступа и историю; провести отдельно согласованные сценарии Telegram.
   Нынешние unit-тесты не подтверждают безопасность полного платёжного цикла.
6. **Качество и запуск:** сохранение темы/языка, переводы, Telegram WebView,
   нагрузка с лимитом 2 CPU/2 ГБ; только затем согласованный VPS-деплой.

Дополнительные риски по чтению кода: конкурентное добавление одного избранного
ещё может конфликтовать; проверки количественных лимитов позиций/алертов не
атомарны; разные одновременные оплаты могут конкурировать за подписку. Эти
сценарии не сертифицированы данным этапом и требуют отдельных регрессионных тестов.

Среда позволяет продолжать эти локальные этапы. Полный продукт, Telegram-платежи
и публичное развёртывание готовыми не объявляются.
